Để ghép **label-driven code search** của bạn với **LLM Wiki / Karpathy-style knowledge vault** thành một hệ thống hoàn chỉnh, tôi sẽ chia thành **8 nhóm công cụ**. Không phải nhóm nào cũng bắt buộc, nhưng nếu muốn chạy ổn từ ingest → gắn nhãn → search → sinh wiki → tái sử dụng tri thức, thì đây là bộ tương đối đầy đủ.

## 1) Nguồn sự thật và theo dõi thay đổi code

Bạn cần một lớp theo dõi version để biết **khi nào phải re-label** và **chỉ re-label phần nào**.

* **Git**: dùng commit hash làm mốc trạng thái, và dùng `git diff` để xác định file/khối code nào thay đổi giữa hai lần indexing. Tài liệu chính thức mô tả `git diff` có thể so sánh giữa working tree, index, tree và giữa hai tree khác nhau. ([Git][1])
* **GitHub Actions** hoặc CI tương đương: để tự động chạy pipeline khi có `push`, `pull request`, release, hoặc theo lịch; GitHub Docs mô tả workflow là quy trình tự động bằng YAML, có thể kích hoạt theo event hoặc schedule. ([GitHub Docs][2])

**Bắt buộc nên có:** Git
**Nên có thêm:** GitHub Actions / CI scheduler

---

## 2) Bộ hiểu cấu trúc code để gắn nhãn tốt hơn

Nếu chỉ đọc code bằng text thuần thì gắn nhãn sẽ dễ sai. Bạn nên có một lớp parse cấu trúc.

* **Tree-sitter**: rất hợp cho bài toán này vì nó là parser generator và incremental parsing library; nó có thể xây syntax tree và cập nhật hiệu quả khi file được chỉnh sửa. Điều này rất hợp với ý tưởng “chỉ xử lý phần thay đổi theo commit”. ([Tree-sitter][3])
* **ripgrep**: dùng làm lớp search lexical cực nhanh để bắt tên hàm, constant, log message, route, config; ripgrep tìm kiếm đệ quy, tôn trọng `.gitignore`, bỏ qua file nhị phân và file ẩn mặc định. ([GitHub][4])

**Vai trò thực tế:**

* Tree-sitter để hiểu class/function/import/call-site
* ripgrep để search nhanh theo text khi cần fallback

---

## 3) Hệ thống quản lý label / ontology nghiệp vụ

Đây là phần “xương sống” của ý tưởng bạn. Không cần công cụ quá phức tạp lúc đầu, nhưng cần 3 thứ:

* **Kho label chuẩn**: có thể chỉ là bảng trong DB
* **Màn hình review**: để người có nghiệp vụ duyệt label AI đề xuất
* **Alias / synonym table**: để map nhiều cách gọi về cùng một label

Phần này **không nhất thiết phải mua công cụ riêng**. Giai đoạn đầu có thể làm bằng:

* bảng `labels`
* bảng `label_aliases`
* bảng `file_label_mappings`
* web admin đơn giản

Điểm quan trọng là:
**LLM chỉ đề xuất label, con người xác nhận label chuẩn**.

## 4) Kho lưu metadata và lớp retrieval

Ở đây có 2 hướng:

### Hướng gọn, dễ làm: **PostgreSQL + pgvector**

* PostgreSQL lưu: file, function, commit, label, mapping, score, review history
* **pgvector** thêm khả năng vector similarity search trực tiếp trong Postgres; tài liệu chính thức nêu pgvector hỗ trợ exact và approximate nearest neighbor search, nhiều khoảng cách đo tương tự, và dùng chung với dữ liệu Postgres còn lại. ([GitHub][5])

Hướng này hợp nếu bạn muốn:

* kiến trúc đơn giản
* ít thành phần
* dữ liệu quan hệ + embedding ở cùng một nơi

### Hướng mạnh hơn cho search: **OpenSearch**

* OpenSearch có **hybrid search**, kết hợp keyword search và semantic search để tăng relevance. ([OpenSearch Documentation][6])
* Rất hợp nếu bạn muốn:

  * BM25 + embedding
  * filter theo label
  * ranking/analytics/search pipeline

### Nếu dùng vector DB riêng: **Qdrant**

* Qdrant có payload metadata và filtering; tài liệu của họ nhấn mạnh có thể index payload fields để filter hiệu quả hơn khi search. ([Qdrant][7])

**Khuyến nghị thực tế:**

* MVP: **Postgres + pgvector**
* Scale lớn, search phức tạp: **OpenSearch**
* Nếu muốn vector-first, filter metadata rõ ràng: **Qdrant**

## 5) Lớp wiki / vault để tích lũy tri thức

Đây là phần ghép với hướng Karpathy.

Trong mô hình đó, kho tri thức thường có:

* `raw/` cho tài liệu thô
* `wiki/` cho các trang markdown do AI tổng hợp
* một file cấu hình như `CLAUDE.md` hoặc `AGENTS.md`
* và câu trả lời tốt có thể được lưu ngược trở lại wiki thành trang mới. 

Nếu muốn đi theo kiểu này, công cụ hợp lý nhất là:

* **Obsidian**: tài liệu chính thức nêu rõ Obsidian lưu note dưới dạng Markdown plain text trong một vault là folder trên local file system, và tự refresh khi có thay đổi từ bên ngoài. Điều này rất hợp với việc để agent hoặc pipeline của bạn cập nhật wiki bằng file Markdown. ([Obsidian][8])

**Điểm mạnh khi kết hợp với hệ của bạn:**

* code search tìm đúng vùng code
* AI phân tích kết quả
* insight tốt được ghi lại thành wiki page
* wiki page lại trở thành tri thức dùng lại cho các lần sau

## 6) Agent / orchestration để nối các bước lại

Bạn cần một lớp điều phối, vì đây không còn là một truy vấn đơn nữa mà là nhiều bước:

1. nhận query
2. map query → label
3. filter candidate code
4. hybrid search / semantic search
5. gọi LLM phân tích
6. nếu output tốt thì cập nhật wiki
7. nếu label thiếu thì sinh đề xuất review

Nếu muốn workflow ổn định, có state, có human-in-the-loop, thì:

* **LangGraph** là lựa chọn đáng cân nhắc. Docs mô tả LangGraph hỗ trợ workflow và agent patterns; workflow có đường đi định trước, agent thì động hơn. Ngoài ra nó cũng nhấn mạnh lợi ích cho long-running, stateful workflow. ([LangChain Docs][9])

Nếu chưa cần phức tạp, bạn vẫn có thể bắt đầu bằng:

* Python scripts
* job queue đơn giản
* cron/CI pipeline

**Khuyến nghị:**

* MVP: script + queue đơn giản
* Hệ thống nghiêm túc hơn: LangGraph

---

## 7) API / service layer để các công cụ khác gọi vào

Bạn nên đóng gói hệ thống này thành service nội bộ.

* **FastAPI** phù hợp nếu bạn muốn làm nhanh service Python; docs mô tả FastAPI là modern, fast, high-performance web framework, dựa trên type hints. ([FastAPI][10])

Các API nên có:

* `/search`
* `/label/suggest`
* `/label/review`
* `/wiki/update`
* `/commit/reindex`
* `/explain/why-this-code`

---

## 8) Graph layer nếu bạn muốn “giải thích được mối quan hệ”

Cái này là **optional**, nhưng rất hợp nếu bạn muốn hiểu mối liên hệ giữa:

* label ↔ feature

* feature ↔ module

* module ↔ service

* service ↔ wiki page

* wiki page ↔ decision / meeting / ADR

* **Neo4j** có thể dùng nếu bạn muốn lưu quan hệ dạng graph; docs mô tả Neo4j dùng property graph model với nodes và relationships. ([Graph Database & Analytics][11])

**Khi nào nên dùng?**

* chưa cần ở MVP
* nên dùng khi bạn muốn truy vấn kiểu:

  * “feature này liên quan service nào?”
  * “label này đang nối với những decision page nào?”
  * “module nào là trung tâm của nghiệp vụ X?”

# Kiến trúc hoàn chỉnh nên chạy như thế nào

## Offline pipeline

1. Lấy tài liệu nghiệp vụ, wiki, notes → đưa vào `raw/`
2. AI mining candidate labels
3. Người có nghiệp vụ review và chốt label chuẩn
4. Lấy source code hiện tại
5. Dùng `git diff` để biết phần thay đổi
6. Dùng Tree-sitter + LLM để gắn label cho file/function thay đổi
7. Lưu metadata vào DB / search engine
8. AI sinh hoặc cập nhật trang `wiki/` nếu có tri thức mới đáng giữ lại

## Online query pipeline

1. Người dùng hỏi
2. Hệ thống map query → label / alias
3. Filter candidate code theo label
4. Search sâu bằng keyword + semantic
5. LLM trả lời
6. Nếu câu trả lời có giá trị lâu dài, ghi ngược về wiki theo mô hình Karpathy-style

# Chốt ngắn gọn

Để ghép hai hướng này thành hệ thống hoàn chỉnh, bạn cần ít nhất 5 lớp:

1. **Version tracking** — Git, CI
2. **Code understanding** — Tree-sitter, ripgrep
3. **Metadata + retrieval** — Postgres/pgvector hoặc OpenSearch/Qdrant
4. **Knowledge vault** — Obsidian + Markdown wiki
5. **Orchestration + API** — LangGraph hoặc scripts + FastAPI

Nếu bạn muốn, tôi sẽ vẽ tiếp cho bạn một **sơ đồ kiến trúc end-to-end** theo đúng ý tưởng này, gồm:
**offline labeling pipeline**, **online query pipeline**, **wiki update loop**, và **human review loop**.
