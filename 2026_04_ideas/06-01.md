Cách giải quyết tốt nhất là không chọn 100% dùng code hoặc 100% không dùng code. Nên tách thành 3 lớp:

1. Source of Truth: tài liệu + testcase Excel

Đây mới là nơi quyết định đúng/sai nghiệp vụ.

Ví dụ:

Requirement / Spec
↓
Testcase Excel
↓
Expected behavior

AI chỉ được dùng phần này để sinh:

- mục tiêu test
- precondition
- input
- expected result
- assertion cần kiểm tra

Không được dùng code để suy luận expected result.

⸻

2. Code / App chỉ dùng để lấy “UI Map”, không dùng để quyết định logic

Problem của bạn là đúng: nếu đưa code cho AI đọc để sinh testcase, testcase sẽ bị bias theo implementation.

Nhưng nếu không có code/app thì AI không biết nút nào, màn hình nào, selector nào để Maestro chạy được.

Giải pháp là dùng code/app chỉ để tạo UI Navigation Map:

Screen name
Element visible text
Button label
Input field
Navigation path
Maestro selector candidate

Ví dụ:

screen: Login
elements:
  - id: email_input
    text: Email
    type: input
  - id: password_input
    text: Password
    type: input
  - id: login_button
    text: Login
    type: button
navigation:
  - action: tap login_button
    next_screen: Home

AI được dùng UI Map để biết cách thao tác, nhưng không được dùng code để biết kết quả đúng là gì.

⸻

3. Sinh Maestro YAML bằng cách merge 2 nguồn

Pipeline nên là:

Requirement / Excel testcase  → Test Intent / Expected Result
App UI Map / Screen Map       → Action path / Selector
---------------------------------------------------------
Maestro YAML                  → Executable evidence

Ví dụ:

appId: com.example.app
---
- launchApp
- tapOn: "Email"
- inputText: "test@example.com"
- tapOn: "Password"
- inputText: "wrong-password"
- tapOn: "Login"
- assertVisible: "Invalid email or password"

Ở đây:

* "Invalid email or password" phải đến từ spec / testcase Excel.
* "Email", "Password", "Login" có thể đến từ UI Map hoặc app inspection.
* Không lấy expected message từ source code.

⸻

Kiến trúc đề xuất

[1] Requirement documents
        ↓
[2] AI sinh Testcase Excel
        ↓
[3] Human review / approve testcase
        ↓
[4] AI sinh Test Intent JSON
        ↓
[5] App crawler / UI parser sinh UI Map
        ↓
[6] AI map Test Intent → Maestro YAML
        ↓
[7] Run Maestro
        ↓
[8] Collect evidence: video, screenshot, log, report

Điểm quan trọng nhất là thêm bước:

Human review / approve testcase

Vì testcase là “luật kiểm định”, không nên để AI tự quyết hoàn toàn.

⸻

Nên thêm một format trung gian

Đừng sinh thẳng Excel → Maestro YAML.

Nên có file trung gian như sau:

test_id: LOGIN_001
title: Login failed with wrong password
source: requirement_login.md
precondition:
  - user is on login screen
steps:
  - input email: test@example.com
  - input password: wrong-password
  - tap login
expected:
  - error message "Invalid email or password" is visible
ui_mapping:
  email_input: unknown
  password_input: unknown
  login_button: unknown
status: need_ui_mapping

Sau đó mới map sang Maestro:

- tapOn: "Email"
- inputText: "test@example.com"
- tapOn: "Password"
- inputText: "wrong-password"
- tapOn: "Login"
- assertVisible: "Invalid email or password"

Lợi ích:

* Dễ review.
* Dễ biết AI đang thiếu selector nào.
* Không bị phụ thuộc code.
* Có thể tái sinh Maestro khi UI thay đổi.

⸻

Quy tắc chống bias theo code

Nên đặt rule rõ:

AI may use source code only for:
- screen name
- route name
- accessibility id
- testID
- visible text
- component hierarchy
- navigation path
AI must not use source code for:
- business rule
- expected result
- validation message
- condition logic
- API response expectation

Expected result chỉ lấy từ:

Requirement
Design spec
API spec
Approved testcase Excel
Manual QA decision

⸻

Giải pháp thực tế nhất

Bạn nên dùng mô hình Dual-Agent:

Agent 1: Test Designer

Input:

Requirement documents
Business spec
API spec

Output:

Excel testcase
Test intent YAML/JSON
Expected result

Không được đọc code.

Agent 2: Flow Builder

Input:

Approved testcase
UI Map
App snapshot
Maestro knowledge

Output:

Executable Maestro YAML

Được đọc UI/code nhẹ, nhưng chỉ để tìm cách thao tác.

⸻

Kết luận

Bạn không nên để AI sinh testcase Maestro trực tiếp từ code.

Cách đúng hơn là:

Spec quyết định cái gì là đúng.
App/UI Map quyết định làm sao để chạy được.
AI chỉ nối hai phần này lại.

Đây là kiến trúc an toàn nhất:

Requirement → Approved Testcase → Test Intent → UI Mapping → Maestro YAML → Evidence

Nếu làm như vậy, testcase không bị “chạy theo implementation”, nhưng vẫn đủ thông tin để chạy automation được.
